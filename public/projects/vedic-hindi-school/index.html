Why I built it: going back to my old school

As a kid I learned to read and speak Hindi at a school that meets on Sundays. Years later I went back to volunteer, and the way it ran hadn't changed: its admin setup and digital systems were more than 20 years old.

So I rebuilt them. Families follow their child's class from their phone, teachers take attendance and post updates in the app, and the office runs enrolment, classes and the calendar from one dashboard.

How it works: one week at the school

Four moments in a school week, and the screen each one happens on.

  1. 01Before term: the office hands out IDs
  2. 02A family signs up
  3. 03Sunday morning: attendance
  4. 04During the week: updates

Before term

The office uploads the class list and gets back an ID for everyone

There's no open sign-up. The admin uploads the roster as a spreadsheet. The dashboard checks every row, sets aside the ones it can't use (a blank name, a role that isn't student or teacher), and returns a CSV with an 8-digit ID for each person, checked so no two repeat.

Sign-up

A parent enters the ID, and the app knows who they are

The app checks the ID exists and hasn't been used, works out whether it belongs to a student or a teacher, and shows the matching form. A student's account takes the parent's email and phone, so the family shares one login. Each ID works once, and nobody can sign up as an admin.

Sunday, 10:00

The teacher marks the roster, and families see it right away

Present or absent for each student, or everyone at once. Publish stays locked until every student has a mark, so a half-taken register never goes out. The teacher can still fix a mark later that day, and past weeks stay in the history.

Architecture: how a notification gets sent

The apps never talk to the push service. They write a job into Firestore, and a Cloud Function does the sending: it works out who should hear about it, looks up their Expo push tokens and sends in batches.

Decoupling it this way means the admin site and the phone app send notifications the same way, and every send leaves a record of how many went out or why it failed.

3 problems I solved to keep a school's data safe

Sign-up had to stay closed

Only enrolled families and staff should get in, and students are children. One-time IDs from the office decide who can register and as what.

8-digit ID 30495817 Student ID · not yet used

The problem

An open sign-up page would let anyone create an account and read class announcements. The school also needed every account tied to a real student or teacher on its roster, and a child's account reachable through a parent.

How I solved it

  • The office issues every ID: a random 8-digit number, checked against existing IDs so none repeat, stored in pendingRegistrations with its role.
  • The app reads that record to check the ID and pick the form: a student form asks for the parent's email and phone, a teacher form for their own.
  • Claiming is a rule, not app logic: an ID can only flip from unclaimed to claimed, and only by the user whose new profile carries the same ID and role.
  • Profiles can only be created as student or teacher, so no client can register an admin.
allow update: if resource.data.claimed == false
  && request.resource.data.claimed == true
  && callerUser().data.uniqueId == resource.data.uniqueId
  && callerUser().data.role == resource.data.role;

The result

Every account maps to someone on the roster, each ID works once, and admins are only ever made by hand.

A modified app can't promote itself

Users can edit their own profile, so the fields that carry access had to be locked on the server, not hidden in the app.

users/{uid}.update({ role: 'admin' }) PERMISSION_DENIED users/{uid}.update({ phone }) allowed

The problem

Anything the app hides, a modified client can still send. If a profile update were trusted as-is, a family could change their role to teacher or admin, or add themselves to another class and read its attendance.

How I solved it

  • A user can update their own profile, but the rule compares the new document with the stored one and rejects any change to role, uid, school ID, email or creation date.
  • Class enrolment (classIds) and teaching assignments are locked the same way, so only an admin can move someone between classes.
  • Reads are scoped too: attendance and class posts check that the caller is in that class, or teaches it.
isAuthUser(userId)
  && request.resource.data.role == resource.data.role
  && request.resource.data.classIds == resource.data.classIds

The result

Families can fix their phone number, but nothing that grants access moves without an admin.

Notifications had to reach exactly one class

A class post should buzz that class's families and nobody else, and Firestore caps how many IDs one query can match.

in30 in30 in12 72 students → 3 queries → 1 send

The problem

Sending from the phone would put push logic, and the list of every family's token, inside the app. A class's families are found by matching its student IDs, and one Firestore in query accepts at most 30 values.

How I solved it

  • Apps only write a job to notificationJobs; a Cloud Function triggered on each new job does the sending.
  • For a class, the function splits the student IDs into batches of 30 and runs one query per batch, then keeps only valid Expo tokens.
  • Messages go through Expo's chunking helper, and the function writes back processed, the time and sentCount, or the error.
for (let i = 0; i < studentIds.length; i += 30) {
  batches.push(studentIds.slice(i, i + 30))
}

The result

One code path for every notification, any class size, and a record of each send.
